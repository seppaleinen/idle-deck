🚀 Part 1: Overview — What idle-deck Is

💡 In One Sentence:
idle-deck turns synchronous developer workflows into an event-driven background pipeline — you label a GitHub issue, idle-deck picks it up, runs an AI agent against it while your machine is free, and comes back with a draft pull request.

🤔 What Problem Does It Solve?

Traditional AI coding assistance is synchronous — you wait for the model to respond. idle-deck is different:

Traditional Chatbot idle-deck
You wait for the model to respond Works while you're away — close your laptop, go to bed
One conversation at a time Queue-based — handles multiple tasks in priority order
No memory of past work Tracks history — every attempt is recorded
You manage the workflow Automated pipeline — from issue to draft PR

💡 The Core Idea

The point is not a chatbot you wait on — it is a queue that keeps working after you close the laptop lid.

  • Label an issue with idle-ready (for features) or idle-hotfix (for urgent fixes)
  • idle-deck picks it up from your GitHub repository
  • Runs an AI agent against it while the machine is idle
  • Comes back with a draft PR and a comment explaining what the agent did
  • You review and merge — autonomy is earned by evidence, not assumed

🎯 Priority Tiers

idle-deck uses a four-tier priority system. Higher tiers preempt lower ones:

P0 — Hotfix 🔥

Trigger: idle-hotfix label

Result: Draft PR

Special: Preempts whatever is running

Timeout: 30 min

P1 — Spec Clarification 📋

Trigger: New issue created

Result: Checklist comment on the issue

Timeout: 15 min

P2 — Feature Implementation ⚙️

Trigger: idle-ready label

Result: Draft pull request

Timeout: 3 hr

P3 — Idle Sweep 🧹

Trigger: Local scheduler (idle capacity)

Result: Files issues for findings

Special: Yields when higher-priority work arrives

🏷️ Label Vocabulary: All labels use the idle- prefix to avoid collisions with your repository's own labels: idle-hotfix, idle-ready, idle-redo, idle-needs-human

⚙️ Part 2: Technical Details

🏗️ Architecture & Components

idle-deck is an orchestration daemon with three adapter seams plus a worker loop. Each adapter has exactly one implementation in the MVP:

📡 Tracker Adapter

MVP: GitHub

Responsibility: Polls for trigger conditions, turns them into tasks; writes comments and labels back

Split into: TrackerSource (inbound parse) + TrackerSink (outbound writes)

Parse() → Task
Comment() / SetLabels()

📊 Priority Queue

MVP: SQLite

Responsibility: Orders work by tier, survives daemon restarts, leases running tasks

Key feature: Lease semantics — expiry without ack = timeout + re-queue

Enqueue() / Dequeue()
Ack() / Nack()

🔧 Harness Adapter

MVP: Remote HTTP service

Responsibility: Sends role + prompt + budget; polls remote execution service

Key constraint: Never names a model — passes a role (plan/do/sweep)

Start() / Abort() / Result()

👷 Worker Daemon

MVP: Go, one worker

Responsibility: Runs the loop: dequeue → dispatch → report → repeat

Preemption: P0 aborts running P2 and takes the slot

Run(ctx) error

😴 Idle Policy

MVP: Harness's GET /health

Responsibility: Probes inference server; if it answers, engine is idle

Definition: Reachable AND has capacity (not busy)

Idle(ctx) → bool

📈 Dashboard

MVP: Read-only review inbox

Responsibility: Shows what concluded, what awaits human, what's next

Listen address: 127.0.0.1:8090

serve command

📐 Domain Model

The domain consists of six entities. Five are durable; Artifact is the record of what a run left behind:

Entity Purpose Key Fields
Repository A source-code repository idle-deck is permitted to act on url, name, allowlisted
Task Immutable statement of intent: do this work, at this priority tier, prompt, state, derived_from
TaskAttempt One execution of a Task. A task has 1..N attempts. outcome, ordinal, remote_session_id
Artifact Something an attempt produced that outlives the attempt kind (PR/branch/comment/report/log), uri
TriggeredBy Provenance — why this task exists event_type, dedupe_key, received_at
TrackerRef Tracker's own identity for a work item tracker, external_id, url

State Machine

Task State:

queued → running → succeeded
running → escalated (terminal failure — never revived)

Attempt Outcome:

started → succeeded
started → retryable_failure → new attempt (if budget remains)
started → timeout → retryable (D17)
started → preempted → P0 evicted the run (D16)
⚠️ Escalation is Terminal: When a task fails three times (2 retries + initial), it is escalated to a human. Recovery happens by creating a new task with derived_from pointing to the old one — never by reviving the escalated task.

📨 Event Contract (GitHub Integration)

🔑 Key Insight: idle-deck polls the GitHub REST API — it has no inbound network surface. No webhook receiver, no listening socket, no signature to verify.

How Polling Works

  • Interval: Every 60 seconds (per GitHub's X-Poll-Interval guidance)
  • Per repository: Four state queries (issues, labels, PRs, etc.)
  • Watermark: One cursor per repo, held in SQLite — seeded at first observation
  • Conditional requests: ETags stored, If-None-Match sent — 304 responses consume no rate limit

Cost Analysis

At 60s across 5 repositories: ~1,200 requests/hour against a 5,000/hour authenticated budget on a quiet repository. Conditional requests reduce this sharply — a tick that finds nothing changed returns 304, which does not consume primary rate limit, and a 304 stops pagination and skips the remaining queries for that tick, so a quiet repo costs almost nothing.

Rate-limit handling. If GitHub answers 429, idle-deck reads the Retry-After header and backs off for that duration (capped at 1 hour) instead of hammering the API. A 429 is not a tick failure: the watermark is left untouched and polling continues to the next repository, so one repo hitting its limit never stalls the others. When remaining quota is low, the poll interval scales up proportionally (up to 5×), so idle-deck stretches its own cadence before it ever needs a 429.

🌐 Remote Execution Contract

🏠 Workspace Ownership: The workspace lives on the remote. The remote owns checkout, git, and Draft PR production. idle-deck receives typed artifacts as data.

Wire Protocol

POST /runs → Start execution Request: { role, prompt, budget, timeout, repo_ref, ticket_ref, attempt_id } Response: { run_id } GET /runs/{run_id} → Poll for result Response: { status: "running" | "succeeded" | "failed" } GET /runs/{run_id}/result → Terminal result Response: { outcome, artifacts: [{ kind, uri, ... }] } DELETE /runs/{run_id} → Abort (cancellation) GET /health → Idle probe Response: { status: "ok", busy: bool }

Authentication

  • Transport: HTTPS/TLS only
  • Client → Server: Authorization: Bearer <token>
  • Token pair: IDLE_DECK_HARNESS_TOKEN (idle-deck) + IDLE_DECK_REMOTE_HTTP_TOKEN (remote) — must match
  • Server → GitHub: Remote holds its own repo-scoped token (not idle-deck's secret)
  • No inbound calls: Remote never calls back into idle-deck

Outcome Taxonomy (§7)

Outcome HTTP Mapping Retryable?
succeeded 200 OK —
retryable_failure 5xx, 429+Retry-After ✓ Yes (consumes 1 retry)
non_retryable_failure 4xx (except 429), 422 budget_exceeded ✗ No (escalates immediately)
timeout Server-enforced (D17) ✓ Yes (D17: timeout is retryable)
preempted 409 Conflict (P0 arrived) ✓ Yes (I7: no timeout consumed)

🎯 Key Design Decisions

1. Framework-Agnostic Means Never Naming a Vendor (D6, D40)

idle-deck passes a role (plan/do/sweep) plus budget and timeout. The harness decides which model fills that role. This is a property of RunRequest's shape — it has no field a model name could occupy.

Not a pluggability claim: The MVP ships one adapter and makes no claim that a second drops in. Instead, it ships a conformance suite (D41) — nine client-observable cases every adapter must pass.

2. Idle Is a Signal, Not a Vibe (D5, D31, D49)

idle-deck asks the harness's GET /health whether a model is reachable. If it answers — reporting reachability, not liveness — the engine is considered idle.

  • No macOS power heuristics
  • No CPU-threshold guessing
  • No "activity monitor" module
  • ✓ One endpoint, one credential

3. Polling, Not Webhooks (D28, D30)

The ticket asked whether the daemon is a public HTTPS endpoint or polls. Polling dissolves the question rather than answering it:

  • No secret whose rotation is a security concern
  • Deny-by-default becomes a config list, not a filter on hostile traffic
  • Level-triggered is resumable — daemon down for a week returns and finds a week of work
  • 60s floor is fine next to 15-minute P1 and 3-hour P2

4. Queue Lease Semantics (D24)

Dequeue() is a lease, never a pop. Expiry without ack = the attempt died with its worker. The queue records the outcome as timeout, re-queues the task, and the retry budget consumes one retry.

Result: A daemon crash cannot strand a task. There is no "lost task" path.

5. Two Automated Retries, Then Escalate (D14)

Third failure escalates:

  • Workspace preserved to debug/<task_id>
  • Diagnostics posted as comment
  • idle-needs-human label applied
  • Task leaves the queue

6. idle-deck Never Merges (D22, D48, D51)

It opens a Draft PR and stops. Autonomy is earned by evidence, not assumed. The pipeline lead merges only on explicit user instruction.

Build Gate (D51): Draft PRs are opened only after go build ./... and go test ./... pass locally. Pre-push hook enforces this — broken branches are never pushed.

7. P3 Sweep: Reporter, Not Author (D43, D44, D45)

A P3 sweep looks for stale TODO/FIXME markers, files one issue per finding labelled idle-needs-human, and may never open a PR.

  • Never produces a pull_request artifact (protocol violation)
  • Never escalates (idle-deck never re-ingests its own writes)
  • ✓ Task.ticket is null for P3 (D44 — the task exists when scheduler ticks, before any issue)

8. One Static Binary, cgo-Free (D32)

Go 1.27, SQLite via modernc.org/sqlite (pure Go), CGO_ENABLED=0. Installs anywhere Go does — no C toolchain, no Xcode CLT.

9. Env-First Configuration (D23, D34, D36)

  • Environment variables, optional YAML file, CLI flags override
  • No .env reader (silent file read = surprise)
  • Secrets never logged, never written to SQLite, never committed
  • Rotation is rotate-and-restart; mid-run expiry = ordinary retryable failure

10. Budget Is Generation-Tokens (D37)

The wire contract carried "budget": 100000 with no unit. Tokens are the natural currency for an LLM harness. No global spend ceiling — idle-deck cannot observe remote-metered spend.
